What gets written

1 Order — one row, POS_WALKIN, straight to COMPLETED
2 OrderItem × 2 — price snapshotted at today's ₱180 and ₱160
3 Payment — provider CASH, status VERIFIED
4 InventoryMovement × 2 — reason SOLD_WALKIN
All four writes sit inside a single transaction.atomic() block. If the receipt printer jams, nothing is committed and the sale stays open.

A receipt is never re-issued under the same number. The attempt counter keeps every copy traceable, so two pieces of paper can never claim to be the same receipt.
Cash is a payment event, not a status transition. Completing this sale records a Payment with provider CASH and status VERIFIED. It does not push the order through CONFIRMED → PREPARING → … — a walk-in order is created already COMPLETED, because goods and money move at the same moment.
Printing. The browser's own print dialog does the work, scoped by @media print to a 72 mm page. No printer driver or ESC/POS library is needed for the prototype.
